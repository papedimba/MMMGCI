# Lot L1 — Authentification, rôles et permissions, audit — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Permettre au personnel de la Mutuelle de se connecter de façon sûre, ne lui donner accès qu'aux actions que ses rôles autorisent (vérifié côté serveur), administrer utilisateurs et rôles, et consulter le journal d'audit.

**Architecture:** Sur le socle L0. Nouvelles tables par migrations `0004`/`0005` ; un `App\Core\Gate` résout les permissions d'un utilisateur ; deux middlewares (`RequireAuth`, `RequirePermission`) protègent le groupe `/admin` ; des contrôleurs simples dans `app/Modules/{Auth,Users,Roles,AuditLog}` reçoivent leurs dépendances par constructeur, câblés dans `routes/admin.php`. Les écrans utilisent un gabarit `layouts/admin.php` minimal, habillé au lot L2.

**Tech Stack:** PHP 8.2 natif (socle L0), MariaDB/MySQL, PHPUnit (dev).

**Spec:** `docs/conception/06-plan-taches.md` (L1), `docs/conception/03-architecture.md` (A6 matrice des rôles, B4 sécurité), `docs/conception/04-base-de-donnees.md` (§3.1), décisions L0 : `docs/superpowers/plans/2026-11-14-l0-decisions-et-reports.md`.

## Global Constraints

- Contraintes L0 inchangées : `declare(strict_types=1)` ; aucune dépendance PHP tierce en production ; SQL uniquement via `Database` avec paramètres liés ; messages en français disant le problème **et** la correction ; `APP_DEBUG=false` par défaut.
- Mots de passe : `password_hash(..., PASSWORD_ARGON2ID)` (repli `PASSWORD_DEFAULT` si Argon2 absent) ; longueur ≥ 12 ; refus des mots de passe courants (liste locale).
- Limitation : 5 échecs / 15 min par couple (e-mail, IP), journal `login_attempts` (B4, T1.2).
- Session : identifiant régénéré à la connexion ; expiration d'inactivité existante (`SESSION_IDLE_MINUTES`, 30).
- Message d'échec de connexion neutre : « Identifiants incorrects. Vérifiez votre adresse e-mail et votre mot de passe. »
- Aucune permission n'est déduite d'un titre ; **aucun rôle ne reçoit `disbursement.approve` ni `disbursement.pay` à l'installation** (A6, décision D3).
- Toute route `/admin/**` (hors connexion et réinitialisation) exige une session **et** une permission vérifiée côté serveur ; accès refusé → 403 journalisé.
- Toute écriture de ce lot (connexion, déconnexion, réinitialisation, utilisateurs, rôles) écrit une ligne dans `Audit` dans la même transaction que la donnée.
- E-mail normalisé : `mb_strtolower(trim($email))` partout (stockage, recherche, limitation).
- 2FA (T1.8) **hors périmètre** : non validée par le commanditaire.

## Review Focus

1. **Dernier administrateur** : désactiver, ou retirer ses rôles à, la dernière personne active qui détient `users.manage` doit être refusé (sinon plus personne ne peut administrer). → Task 6.
2. **Pulvérisation d'identifiants** depuis une seule IP sur de nombreuses adresses : au-delà de 20 échecs / 15 min par IP, toute tentative depuis cette IP est bloquée. → Task 2.
3. **Jeton de réinitialisation** réutilisé, expiré, ou utilisateur désactivé entre-temps → refusé ; après réinitialisation, les autres sessions ouvertes sont déconnectées. → Task 5.
4. **Adresse e-mail saisie avec majuscules et espaces** (« Jean.Kouassi@Exemple.CI ») : connexion, unicité et limitation la traitent comme la même adresse. → Tasks 3 et 6.
5. **Redirection après connexion** (`?retour=`) : seules les adresses internes commençant par `/admin` et pas par `//` sont suivies ; sinon `/admin`. → Task 3.
