# Lot L6 — Cotisations, finances, double validation, fonds de solidarité — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Tenir les cotisations, le grand livre des recettes et dépenses, les reçus, et le **circuit de décaissement à double validation** (initiateur ≠ deux approbateurs distincts ≠ jamais de paiement direct), avec le fonds de solidarité comme compte dédié. Toute valeur que le cahier des charges ne fixe pas (montants, périodicité, seuils, règle « à jour », politique de solde insuffisant) reste « non configuré ».

**Architecture:** Module `app/Modules/Finance/` (grand livre, comptes, catégories), `app/Modules/Contributions/` (types, appels, encaissements, reçus), `app/Modules/Disbursements/` (circuit). Migrations 0010 (tables) et 0011 (permissions, paramètres). Les règles du circuit vivent dans un **service métier unique** (`DisbursementService`) qui travaille en transaction avec verrou de ligne, doublé de contraintes en base ; les écrans n'appliquent aucune règle. Les écritures financières sont **immuables** : on corrige par contre-passation. Écrans bâtis sur le kit `ui()` du lot L2, impression via `layouts/print`.

**Tech Stack:** PHP 8.2 sans framework, MariaDB/MySQL (PDO, DECIMAL pour les montants, jamais de float), PHPUnit. Aucune dépendance nouvelle.

**Spec:** `docs/conception/03-architecture.md` (A5.3 circuit de décaissement, A6 matrice), `04-base-de-donnees.md` §3.4 et §4, `06-plan-taches.md` (L6, T6.1–T6.10), cahier des charges art. 10, 13, 14, 15, 17. Décisions précédentes : `docs/superpowers/plans/2026-11-15-l{1,2,5}-decisions-et-reports.md`.

## Global Constraints

- PHP ≥ 8.2, `declare(strict_types=1)`, aucune dépendance Composer en production, requêtes préparées ; migrations versionnées 0010 et 0011 (jamais modifier une migration appliquée).
- Africa/Abidjan, **XOF**, interface en français ; CSP stricte (aucun style/script en ligne) ; kit `ui()` ; une `h1` par page ; cibles ≥ 44 px au toucher ; téléphone d'abord.
- **Montants** : `DECIMAL(15,2)` en base, objet `Money` du socle côté PHP, jamais de `float` ; `CHECK (amount > 0)` sur toute écriture et tout décaissement ; XOF affiché sans décimales superflues selon `Money`.
- **Jamais de règle inventée** : montant de cotisation, périodicité, seuils d'approbation, règle « membre à jour », politique de solde insuffisant, plafonds, durée de conservation = paramètres `non_configure` (bandeau « paramètre en attente de validation par les instances »). Sans montant validé : **aucun appel de cotisation automatique** ; sans règle « à jour » : on affiche le nombre d'impayés, jamais le mot « à jour ».
- **Circuit de décaissement (A5.3)** : jamais moins de **deux approbations** par révision ; l'initiateur n'approuve jamais ; deux approbateurs **distincts** ; rejet = état final ; une modification substantielle (montant, bénéficiaire, compte, motif, pièces) crée une nouvelle révision et rend caduques les approbations précédentes sans les effacer ; **un seul paiement** par demande (`UNIQUE` en base) avec justificatif obligatoire ; le payeur n'est jamais l'initiateur ; paiement refusé si le solde du compte est insuffisant (politique par défaut : bloquer ; paramétrable) ; chaque transition est auditée.
- Aucune permission d'approuver ou de payer n'est attribuée par défaut : le module de décaissement **refuse de fonctionner** (écran explicatif) tant que moins de deux personnes distinctes disposent de `disbursement.approve`.
- Écritures financières **immuables** : aucune route ni méthode ne modifie ou supprime une transaction, un paiement, un reçu ; annulation = contre-passation (`reversal_of_id`), montant identique, sens opposé.
- Chaque écriture est auditée ; verrous toujours dans l'ordre : demande de décaissement → compte → séquences (et paiement/reçu → compte → séquences) pour éviter tout interblocage.
- Permissions existantes : `contributions.view|manage|export`, `finance.view|control`, `disbursement.initiate|approve|pay`, `solidarity.view|manage`. Nouvelle (0011) : `finance.manage` (comptes, catégories, ressources hors cotisations), attribuée aux rôles qui détiennent déjà `contributions.manage` ou `solidarity.manage`.
- Toute route `/admin` : `[$requireAuth, $permission('x')]` ; `AdminRouteSweepTest` reste vert ; suite existante (500 tests) verte ; ne pas affaiblir d'assertion.

## Review Focus

1. **Contournement du double contrôle** : approbation par l'initiateur (y compris via un second rôle), deux approbations du même utilisateur, approbation d'une révision caduque, double clic / double soumission du paiement, paiement sans approbation, passage direct brouillon → payé par POST forgé.
2. **Concurrence** : deux approbateurs simultanés, une approbation pendant une modification substantielle, deux paiements simultanés, deux encaissements de la même cotisation (idempotence), numéros de reçu jamais dupliqués.
3. **Montants** : arrondis, montant 0 ou négatif, montant énorme, séparateurs saisis à la française (« 12 500,50 »), encaissement supérieur au dû, paiement partiel puis solde, contre-passation d'un paiement déjà contre-passé.
4. **Fuites et périmètre** : un utilisateur avec `finance.view` voit-il des pièces ou données de santé ? un adhérent hors périmètre délégué dans les cotisations ? exports financiers (injection de formules, mêmes protections que les adhérents) ?
5. **Cohérence du solde** : solde = ouverture + Σ recettes − Σ dépenses, recalculable ; fonds de solidarité = compte dédié sans mélange ; une dépense ne sort jamais d'un compte sans décaissement approuvé (sauf frais enregistrés explicitement par `finance.manage` avec référence d'autorisation : à trancher et documenter).

## Rulings de conception (à confirmer par les instances)

- **Politique de solde insuffisant** : non configurée → défaut technique « bloquer » (le plus sûr) ; coût si les instances veulent alerter seulement : un paramètre à valider.
- **Payeur ≠ initiateur** : appliqué par défaut (A6), paramétrable ; coût : un trésorier unique qui initie ne peut pas payer.
- **Population concernée par un appel groupé** : non définie par le cahier des charges ; par défaut les membres au statut `actif` avec bandeau « à valider » ; coût : à ajuster quand les instances précisent.
- **Dépenses hors décaissement** : interdites dans ce lot (toute sortie passe par le circuit) ; frais courants éventuels à décider par les instances.
- **Budgets et engagements (T6.9, P2)** : reportés, hors de ce lot.
- **Aucune permission d'approuver/payer attribuée** par défaut : le module de décaissement est inopérant tant que deux approbateurs distincts ne sont pas désignés (décision déjà prise en conception A6).
